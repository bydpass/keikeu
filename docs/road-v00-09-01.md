# Road v00.09.01：原生 iOS

状态：规划草案及隔离可行性验证，更新于 2026-09-22。原名 Road v09.01；已有授权覆盖新建分支、继续规划、调研复核、入口视觉原型及最小可行性验证；尚未启动产品实现。规划分支 `codex/road-v00-09-01-plan`，起点 `d0a557a`，沿用主工作树，不另建目录。历史输入见[转交清单](road-v09-01-handoff.md)，当前实现见 [PROJECT](PROJECT.md)。

## 目标与范围

让 iPhone 使用 SwiftUI 和原生编辑、导航、分享组件完成现有移动 Paper 流程，尽可能保留 Rust 规则与持久化语义。成功标准是可连续创作、可靠保存与恢复，并与现有 Mac iCloud 客户端交换同一 Paper v4 文件。

已确定：移动端原生化；Rust 尽可能复用；Mac 重构延后；Windows 保留当前结构；旧 B14 关闭，不继承为待办。2026-09-21 用户选择同时重新设计功能与信息结构，并要求先用头脑风暴斟酌。下表是讨论起点，功能范围和 CP2 内容尚未冻结；数据安全及格式兼容约束持续保留。

| 本 Road 包含 | 本 Road 不包含 |
| --- | --- |
| iPhone 本地与用户主动启用的 iCloud Vault | Mac 界面重构、Windows 适配、Android、正式 iPad 验收 |
| Paper 创建、编辑、多页、Tags、保存、重开、列表与 Unicode 搜索 | 桌面 Index、文件夹、Trash、旧格式迁移等全功能对等 |
| 本机草稿、冲突副本、失败恢复、单 Paper 导出、中英文界面 | Python 退役、外部 Alpha、TestFlight 与公开发布 |
| 原生输入法、键盘、安全区、导航及后台恢复 | 改变 Paper v4 格式、自动保存正式稿、自建同步服务 |

现有移动能力用于逐项判断保留、调整或延后，不作为首版必须照搬的清单。私有草稿持久化与正式保存分开，不能把已写草稿提示成已保存 Paper。

## 当前实现与拟定分工

| 部分 | 当前事实 | 本次规划方向 |
| --- | --- | --- |
| 纯规则 | `crates/keikeu-core` 无 Tauri、Apple 或文件访问 | 保持职责；共享黄金样本验证编解码及 Unicode 比较 |
| 保存与恢复 | `paper/store.rs`、`host/mod.rs`、`private.rs`、`conflicts.rs` 拥有快照、会话和保全 | 抽离实际需要共享的运行代码，保留现有安全行为，不另写 Swift 规则 |
| 调度与路由 | `dispatch` 使用 AppHandle、Tauri 线程池与 PythonLease；Router 同时处理桌面分流 | Tauri 留下桌面接入层；iOS 不带 Python 分流，保留存储身份与代次约束 |
| Apple 能力 | 现有 Swift 提供文件协调、云状态及系统导出 | 复用并检查调用线程、生命周期和回调边界；系统界面由原生客户端呈现 |
| 原生界面 | 当前 iPhone 仍为 Vue 工作面 | SwiftUI 管可见状态；输入控件按组合输入、选区与滚动的实测选择原生实现 |

桥接尚未选型。CP0 先验证现有 C ABI＋JSON 思路能否支撑 Swift 调用 Rust，明确字符串长度、内存释放、句柄生命周期及错误返回；它是候选方案，不是已批准的新接口。只有出现具体维护或正确性缺口才比较生成式桥接；新增依赖先按 RULES §2 处理。

现有 `Host.swift` 的导出会等待系统面板返回，`dispatch` 则先释放存储锁。新入口必须保留“面板不阻塞草稿队列”的行为；不能把现有阻塞调用直接放到 Swift 主线程。取消等待不等于撤销已开始的写入，结果丢失进入只读核对。

## 数据接续与测试隔离

1. 先确认旧候选的包身份、sandbox 与 iCloud 容器，以及新测试包可访问的范围。独立包不会自动取得旧 sandbox；不能把安装成功当成数据接续成功。
2. 本地内容先导出／复制到合成测试位置，核对文件清单与字节，再验证新客户端读取、编辑和重开。未知元数据与坏文件保留，失败不更改源件。
3. 旧私有草稿与恢复副本有独立位置和身份。CP0 明确其导出或接续路径；完成保全前不覆盖安装、不卸载旧应用，也不清空旧恢复区。
4. 双端测试使用专用合成 Vault，记录 Mac 与 iPhone 各自的源码、包与配置。若隔离包不能访问既定云容器，先解决测试路径，不直接改日常库补测。
5. 将“本机写入成功”“系统同步状态”“另一端读回”分开显示和取证。不能通过反复点击保存制造通过结果。

## 验证与证据

- 格式：复用 Python／Rust 黄金样本，检查多页、空字段、未知元数据、多语言、组合重音及坏格式原文保留。
- 写入：验证替换前失败、替换成功但响应丢失、外部变更、旧代次返回；未知结果核对不得重新写入。
- 恢复：验证较新草稿不被旧保存清除、保全失败明确报告、重启能取回最后落盘版本、导出取消不删除原稿。
- provider：同编号新建按实际改名副本或原生冲突分别记录，不要求人为制造某种结果，也不以一种结果替代另一种能力证据。
- 系统不可用：在新架构明确后判断账号／容器／Drive 情况的适用性。合成故障能证明应用分支，不能冒充真实系统观察；旧 B14 不重新打开。
- 桌面回归：修改共享 Rust／Apple 部分时跑直接测试和隔离 Mac 冒烟；最终候选跑 Python、前端、Rust 及构建检查。纯文档阶段只跑文档检查。

每条验收记录绑定提交、包摘要、设备／系统、日期、操作、结果及未验项。旧 v09 的 302／142／22 项通过和 Mac 冒烟仅作为基线，不记为本 Road 通过。

## 已确认的使用主线

2026-09-21 用户说明：突发灵感随手写，写完放下并得到稳定私密的 Paper；再次拿起时用于吸收与创作。整理为主动选择，可以直接以 flash 样式只读使用 Paper，也可以整理为更精密的 flashcard 后使用。是否作为独立文件、如何关联来源与处理更新，尚未决定。

参考内容应能配合主流手机写作软件使用，包括系统备忘录；期望小窗同屏。具体平台能力与替代交互尚待研究，不提前承诺。用户已指定由 WorkBuddy 专家团承担[市场与平台调研](road-v00-09-01-research-brief.md)，报告已返回并完成首轮有限复核，存在键盘权限、输入功能和软件现状等纠正／待核实项；详见同一委托文档的复核记录。用户已明确理想形态为 cheatsheet 式持续可见；短暂翻看再返回属于 opt-out 基础功能，不能用它替代持续展示目标。技术可行性仍待验证，首版是否能够达成须据证据单独决定。

### 持续展示与退出方式

- 核心体验目标：在外部编辑器写作时，参考 Paper／flashcard 持续可见。方案评估应覆盖实际打字过程，而非只在停止输入或切换键盘时能查看。
- 用户主动退出持续展示后，仍可临时打开、翻看并返回编辑器；此基础功能持续保留。
- “是否整理内容”与“是否持续展示”是两个独立选择：未经整理的 Paper 也可用于持续参考，整理后的 flashcard 也可仅临时翻看。
- 目前未批准键盘扩展、PiP 或其他实现。若平台验证不能达成目标，明确呈现缺口与可选调整，由用户决定；不静默降低目标。
- 展示内容已确定：在主应用选好一份参考内容后持续展示；更换整份内容时回主应用切换，操作习惯参考视频网站的小窗播放，但不等于已选择 PiP 技术。
- 小窗必须支持当前内容的滚动与翻页；这两种阅读操作不要求返回主应用，也不插入确认、搜索或其他额外步骤。小窗负责只读参考，不承担内容编辑与库内检索。
- 验证重点：外部编辑器实际输入时参考内容持续可见；小窗滚动、翻页后能继续创作，检查编辑器光标、选区与组合输入状态是否受影响。静态截图或仅能展示视频的窗口不能证明这些要求通过。

## 头脑风暴顺序

先讨论实际场景，不从页面数或控件样式起步。每轮收敛一个决定，记录选择、理由和延后项；工程检查点随已接受的产品方向调整。

1. 使用动机：手机最常在哪种时刻打开，离开时希望完成什么？
2. 核心流程：快速记录、整理成 Paper、连续写作、查阅旧内容各占什么位置？
3. 内容关系：继续以 Paper／Page 为中心，还是需要新的进入与组织方式？若影响文件模型，先单独提出兼容方案。
4. 信息结构：由前面场景推导首屏、主要导航、编辑入口和恢复入口。
5. 范围取舍：列出首版必须、可延后和明确排除项，再调整 CP0–CP4。

使用动机及两条使用路径已明确。持续参考的内容选择与阅读操作已明确。下一步按“外部编辑器输入＋持续展示＋小窗滚动／翻页”验证平台可行性，再冻结接口、布局与实现选型。
