keikeu · Paper v4 · offline repair

Paper 坏了，先保住原文，再修结构。

这份手册供能使用普通纯文本编辑器的人离线修复 Paper v4。你不需要理解程序代码， 但必须逐字保留不确定的作者内容，并只改能够确认的结构。

最重要的边界：keikeu 不会自动改写损坏文件，也不会从损坏内容生成 半成品 Paper。先在 Finder 复制原文件，再编辑副本或有备份的文件；若保存结果未知， 先点“复制保留草稿”，绝不再次点击保存。

Safe route

最短安全路线

  1. 在 repair 界面记录相对路径和错误类别；错误信息不会显示正文。
  2. 点“在 Finder 中显示”，在 Finder 中复制该 .md 文件作为备份。
  3. 用纯文本编辑器打开原文件。macOS 文本编辑应先切到纯文本模式，不能保存为 RTF。
  4. 对照本页完整示例，只修明确损坏的 fence、字段、marker、空行或 Tags。
  5. 以 UTF-8 保存；整份文件统一使用 LF，或统一使用 CRLF。
  6. 回到 keikeu 点“重新检查”。仍失败就保留备份，不要猜测或删除陌生文字。
  7. Paper 可打开但 Library 提示 Index 过期时，才点“显式重建 Index”。

Finder 中的文件名必须是 frontmatter 中 code 加 .md；例如 K-20260802-001.md。不要为了消除错误随意更改 code、日期或文件名。

Copyable canonical file

一份完整 Paper v4

下面包含四种 type 状态、标题中的连字符、正文保留 marker 和 Tags。

---
type: paper
schema_version: 4
code: K-20260802-001
created: 2026-08-02T12:00:00
updated: 2026-08-02T12:30:00
display_name: 夜车灵感
---
# K-20260802-001

<!-- keikeu:page {"name":"起点","type":"summary"} -->
列车离站前，她决定把一句话写下来。
<!-- /keikeu:page -->

<!-- keikeu:page {"name":"橘\u002d子","type":"snapshot"} -->
作者正文中的结束 marker 要多一个反斜线：
\<!-- /keikeu:page -->
作者原本写了一个反斜线时，文件里要有两个：
\\<!-- keikeu:page {"name":null,"type":null} -->
<!-- /keikeu:page -->

<!-- keikeu:page {"name":null,"type":"whisper"} -->
这一页没有标题，但有碎碎念正文。
<!-- /keikeu:page -->

<!-- keikeu:page {"name":"未分类页","type":null} -->
<!-- /keikeu:page -->

## Tags

- 夜车
- 重逢,旧友

示例中的 \u002d 是文件里的实际六个 ASCII 字符；解析后页标题仍是“橘-子”。

Anatomy

从上到下只有四层

部分必须满足可以改什么
frontmatter 由独占一行的 --- 包住；必须各有一次 type、schema_version、code、created、updated。 display_name 可省略；陌生字段先保留，不要删。
文档标题 # code 必须与 frontmatter 和文件名完全一致，之后恰好一个空行。 通常不改。
page block 至少一页；start marker、正文、end marker 成组，相邻页之间恰好一个空行。 可修 name、type 和错误 marker；正文不确定就不改。
Tags 唯一的 ## Tags 位于最后；非空项严格写作 - 值。 空 Tags 只保留标题；逗号是普通字符，不是分隔符。

不允许额外 HTML comment、游离文字、空格行、重复 section 或 Tags 后文字。 页面正文可以包含任意 Markdown，但碰到保留 marker 整行时必须按“转义规则”处理。

Names and types

name、content、type 与空值

name · 页面标题

字符串表示标题；null 表示没有标题。推荐用 null，不要用空字符串冒充无标题。

content · 正文

位于两个 marker 之间，不带字段名。两 marker 相邻表示空正文，但此时 name 必须非空。

type · 可选标记

"summary" 显示“总结”，"snapshot" 显示“高光”，"whisper" 显示“碎碎念”。

null · 不显示标签

type:null 表示没有类型；不能写 ""、"highlight"、中文显示名或其他值。

一份 Paper 最多一页 summary，但可以有很多 snapshot、 whisper 或 null。每页必须至少有非空标题或非空正文。

Reversible escaping

三处反斜线，各有固定用途

位置文件写法原因
frontmatter value \ 写成 \\；逻辑换行写成 \n；CR 写成 \r。 frontmatter 一行只保存一个 scalar。未知的 \x 会原样保留。
page marker 的 name 标题中的每个连字符 - 写成 JSON \u002d。 HTML comment payload 不能出现原样 --；解析后标题恢复原字符。
page content 的保留整行 在保留行原有的零个或多个反斜线前，再加一个 \。 防止正文被误判为 start/end marker；解析时只移除恰好一个。

只有两类正文整行属于保留 marker：

  • 以 <!-- keikeu:page 开头并以 --> 结尾的整行；
  • 精确等于 <!-- /keikeu:page --> 的整行。

不要给普通正文中的局部文字、缩进 marker 或其他 HTML comment 随意加反斜线。 只处理完整保留行，才能保持往返可逆。

Bytes

UTF-8、换行与空行

  • 保存为无 BOM 的 UTF-8 纯文本；不要保存为 RTF、Word 或富文本。
  • 全文件统一 LF 或统一 CRLF；不能混用，也不能出现裸 CR。
  • keikeu 正常保存固定输出 LF，并在文件末尾保留一个换行。
  • 标题后、相邻 page block 之间、最后一页与 Tags 之间恰好一个空行。
  • 正文首尾空行属于作者内容；不要为了“整齐”删除。
  • 空 Tags：## Tags 后直接文件结束；非空 Tags 与标题之间一个空行。

Error dictionary

常见错误在说什么

错误片段含义先检查
missing the opening frontmatter fence第一行不是 ---。文件是否被富文本工具加了前缀。
frontmatter repeats key同一 frontmatter key 出现两次。只保留确认正确的一项；陌生值先备份。
heading must exactly match its code# code 与 frontmatter 不同。同时核对文件名；不要猜一个新 code。
page N ... invalid JSON第 N 页 marker 的 JSON 引号、逗号或括号损坏。对照 {"name":null,"type":null}。
invalid typetype 不在三个英文值或 null 中。不能写中文显示名或 highlight。
nested start marker正文中的 start marker 没有转义，或上一页缺 end marker。先找配对关系，再决定是否给正文行加反斜线。
unescaped reserved marker正文保留行缺少一个前置反斜线。只在该完整行最前面加一个 \。
missing its end marker第 N 页没有配对的结束 marker。不要把正文中原有 marker 当结构；对照上下页。
separated by one blank line页面、标题或 Tags 周围空行数量不对。结构之间恰好一个完全空白行。
Tags ... '- value'Tags 列表使用了错误符号、空项或续行。每个非空 tag 独占一行并以 - 开头。
valid UTF-8 / mix LF and CRLF文件编码或换行方式不一致。在纯文本编辑器中转换整份文件，不能局部替换。

错误中的相对路径用于 Finder 定位；page N 只在 parser 能可靠判断时出现。 keikeu 不会把损坏正文、真实绝对路径或半解析 Paper 放进错误信息。

Unknown save

看到“保存结果未知”时

  1. 不要再次保存。响应丢失不等于写入失败，重发可能覆盖或冲突。
  2. 重启本地 Core；keikeu 只会运行只读 paper.reconcile_save。
  3. 若进入 unknown-save repair，先点“复制保留草稿”。复制内容只进入你主动选择的剪贴板。
  4. 点“在 Finder 中显示”，复制磁盘文件作备份，再按本页修结构。
  5. 点“重新检查”。keikeu 会比较旧 baseline、submitted 草稿和当前磁盘，不会重放保存。
  6. 若结果为 stale，说明出现第三份内容、身份变化、目标缺失、重复 code 或 Vault 已变化；不要自动合并。

普通打开的 repair

没有可信 draft；界面只显示安全路径、结构原因、Finder 与重新检查。

未知保存后的 repair

内存中保留 submitted 草稿与旧 baseline；关闭仍受保护，只有明确放弃才清除。

Return to app

修复完成的判断顺序

  1. 回到 repair 界面点“重新检查”；不要先从 Finder 直接覆盖其他 Paper。
  2. Paper 能完整打开，页数、标题、正文、类型和 Tags 与预期一致。
  3. Library 若仍显示该路径损坏，刷新并再次核对相对路径。
  4. 只有出现“Index 可能过期”时，点一次“显式重建 Index”。Index 可重建，不是作者权威。
  5. 若仍失败，保留原件、副本和复制的草稿，停止猜测；错误可能不是本页能安全修复的结构问题。

不要删除唯一原件、不要把另一个 Paper 的 code 复制过来、不要清空不认识的 frontmatter， 也不要为了消除 Index 警告改写正文。Markdown 是作者权威，Index 只是本地派生投影。

产品与工程规则最终以 SPEC、 RULES 和 Road v0.6 设计 为准。
