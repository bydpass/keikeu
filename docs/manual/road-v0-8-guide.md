# Road v0.8 导读：从桌面创作到 iPhone 与 Mac 同步

> 2026-09-04 · 人工理解手册，依据本次重构后的 [活动计划](../../PLAN_road_v0_8.md) 与
> [ADR-0009](../architecture/decisions/0009-unified-rust-core-transition.md) 编写。
> 下文的阶段、界面和故障例子解释未来目标，不是已实现功能或测试记录。
> 当前软件 CP0 尚未启动；阶段状态查 [PROJECT](../PROJECT.md)，合同以活动计划与
> [SPEC](../SPEC.md) 为准。手册不增加功能、验收条件或操作授权。

阅读顺序：先看交付范围和架构，再看阶段表；保存、恢复和同步的例子解释计划为何设置这些门槛。

## 1. 这次要交付什么

作者可以在 iPhone 上创建一份多页 Paper，编辑、保存、重开、搜索或导出单篇 Markdown；
主动启用 iCloud 后，能在 Mac 上继续处理同一份 Paper，再回到 iPhone。界面支持中文和英文，
作者写下的正文、名称与 Tags 保持原样。本机恢复稿用于意外退出后找回已持久化的草稿。

v0.8 的交付边界有三处容易混淆：

| 环境 | 候选必须提供的能力 |
| --- | --- |
| iPhone 本地 | 核心创作、列表搜索、本机恢复、单篇导出 |
| Mac 与 iPhone 共享云端 | 核心创作、两端往返、下载与同步状态、冲突保全和恢复 |
| Mac 本地 | 完整保留既有资料管理，包括文件夹、Index、废纸篓、历史迁移和外部编辑器能力 |

“Mac 上已有”不等于“云端 Vault 也有”。v0.8 云端和移动端的能力较窄，完整移动资料管理、
整库导出与正式 iPad 验收不在本次范围。iCloud 往返属于必需交付，仅有 iPhone 本地版本不能完成 v0.8。

本地仍是默认选择。启用 iCloud 需要作者主动选择，不会把已有本地 Vault 自动搬到云端。

## 2. 为什么保留界面，却逐步更换核心

先分清几个名称：Vue 负责界面和编辑中的状态；Tauri 提供应用壳；host 是连接界面与原生能力的
宿主层；Core 处理 Paper 规则和文件操作。sidecar 是由桌面应用管理的独立 Python 子进程。

当前已接受的桌面执行链是：

```text
Vue → Tauri / Rust host → JSONL protocol v2 → Python service / Core → Markdown / Index
```

候选阶段按所选存储使用不同后端；同一客户端只按当前存储选择一条写入路径：

```text
v0.8 Mac 本地       → 既有 Python 后端 → 本地 Vault（完整桌面能力）
v0.8 iPhone 本地    → Rust Paper Core → 沙盒 Vault
v0.8 Mac/iPhone 云端 → 同一 Rust Paper Core → Apple 原生文件协调 → 共享云端 Vault

候选后的独立收口   → 桌面剩余能力迁入 Rust → 对等与切换验收 → Python 产品运行时退役
```

这条路线复用已有界面，先完成移动创作所需的共享规则，再迁移桌面剩余能力。代价是过渡期要维护
两套实现及对照测试；收益目标是最终只维护一套产品 Core。双后端的结束点被明确放在首轮外部 Alpha 之前。

[ADR-0009](../architecture/decisions/0009-unified-rust-core-transition.md) 比较了保留双后端、
嵌入 Python 和逐步迁入 Rust。选择 Rust 是维护决策；不能把它解释成“iOS 无法运行 Python”。
Python 退役指分发应用不再依赖它，开发期仍可用它做对照。

换语言也不等于换作者文件格式。Paper v4 继续有效：同一组经审阅的合法、非法和边界样本
交给 Python 与 Rust 检查，比较结构、序列化和拒绝原因。这组样本称为 golden corpus；
如果 Python 行为与书面合同冲突，先裁定差异，不能照搬旧实现中的错误。

### 接口保留到哪一层

`bridgeRequest(method, params)` 是前端发出请求的边界。保留它，有助于复用调用入口，
但不表示所有平台的方法和返回字段完全相同。DTO 是跨边界传递的数据结构；能力声明告诉界面
当前后端实际支持什么。共享 Paper 数据、存储能力与 host 新方法要在 CP0 分开约定。

例如移动端搜索可读取受支持的 Paper，不维护桌面 Index。它不能返回虚构的
`index_state=current` 来让旧界面误以为 Index 正常。旧 Python JSONL protocol v2 在过渡期冻结，
host 的新增能力不直接塞进旧协议；具体字段和方法签名仍由 CP0 冻结。

每个客户端对所选 Vault 只启用一个受控写入后端。Python 保存出错后自动改用 Rust 重写，
会让未知结果更难判断，因此计划禁止这种回退。Mac 和 iPhone 仍可能同时写同一云端 Paper，
这类跨设备并发需要另外处理。

## 3. 为什么按这个顺序施工

CP 是阶段检查点，Gate 是进入或离开阶段前需要满足的条件。“退出条件”表示阶段何时可以结束，
不是用户退出应用。计划把每个阶段都写成“输入条件—交付物—检查—退出条件—失败停点”。

| 顺序 | 这一阶段回答的问题 | 主要证据与停止位置 |
| --- | --- | --- |
| 独立关闭保护修复 | 在 Paper 之外的页面正常关闭时，未决写入也受到保护吗？ | Paper、Library、Vault、阻塞页面的聚焦检查与正常关闭 smoke；接受后才进入新 Road |
| CP0：合同冻结 | 谁能写什么？失败后保留什么？如何判断操作结果？ | 方法、能力、错误与状态合同经开发者接受；本阶段只做文档，不建 iOS 探针 |
| CP1：Apple 可行性 | 实际 iPhone、Mac 和共享容器能支撑选定路线吗？ | 合成文件的原生调用、沙盒、生命周期、往返和冲突保全；必需条件缺失就停，不进入 CP2 |
| CP2：共享 Core | Rust 能正确读写现有 Paper v4 吗？ | 对照样本、损坏输入、过期快照、路径边界和失败写入测试 |
| CP3：iPhone 本地创作 | 作者能在实体手机上完成核心循环并恢复草稿吗？ | 触屏、输入法、多页、保存重开、导出、前后台与终止恢复；同时检查 Mac 回归 |
| CP4：两端 iCloud | 完整产品在离线、并发、未下载和冲突时如何工作？ | 两端往返与失败恢复、原始冲突字节保全、存储切换；同步缺证不能进入候选验收 |
| CP5：跨端候选验收 | 同一源码版本的 Mac/iPhone 候选是否共同满足范围？ | 必需场景结果、无未解决 P0/P1、开发者接受，以及后续收口交接 |
| 独立统一核心收口 | Rust 是否已接管全部桌面能力，能安全退役 Python？ | 副本上的完整桌面对等、切换与移除后的回归；未通过不能开始外部 Alpha |

CP0 不再要求进入之前就冻结它负责产出的合同。当前还需要关闭保护修复通过，以及开发者明确批准
计划版本和软件 CP0 seed；“同意重写计划和手册”没有完成这些步骤。

CP1 和 CP4 都碰同步，但目的不同：CP1 用最小探针尽早识别路线是否被平台能力阻断；CP4 把这些
能力接入完整创作、切换和恢复流程。这样不会等到 Core 和界面投入完成后才发现共享容器不可行。

候选后的收口是独立工作，因为手机能创作并不能证明桌面废纸篓、历史迁移、Index 和系统动作已完成
迁移。CP5 交接剩余能力清单，后续再形成具体施工计划；不能把桌面功能省掉来宣布“已经统一”。

## 4. 保存、草稿与对账分别保护什么

正式 Paper 是作者在 Vault 中的 Markdown 文件；编辑中的草稿是尚未确认保存的状态；
本机恢复稿是已成功持久化的草稿副本，不进入 Vault 或两端同步。恢复稿不能代替正式保存。

CAS 可以理解为“确认文件还是打开时那一版，才允许替换”。如果外部编辑器已经改过文件，
这次保存应停下来，避免用旧草稿覆盖外部编辑结果。CAS 也不能代替跨设备文件协调。

| 发生什么 | 为何要分开判断 | 计划要求的处理 |
| --- | --- | --- |
| 正式文件替换前失败 | 本次写入明确未提交 | 保留草稿，显示失败；不能报保存成功 |
| 文件已保存，但响应丢失 | 界面无法确定磁盘结果，称为 `commit_unknown` | 保留草稿，先只读对账，不自动重发写入 |
| 文件已被外部修改 | 打开时的快照过期，继续写可能覆盖别人刚写的内容 | 阻止覆盖，保留草稿，用只读检查确认当前状态 |

“对账”是读取状态来确认之前发生了什么，不是再次执行保存。即使界面显示超时，文件也可能已成功
落盘；自动重试可能引入第二次变更。恢复与后续用户操作要根据对账结果处理，不能把所有失败归成重试按钮。

### 一次旧保存，不能清除较新的草稿

假设作者保存草稿修订 12，随后又产生修订 13；修订 12 的成功响应稍后才回来。
此时只能清除对应已保存修订的恢复记录，修订 13 仍要保留。修订号只是说明身份的例子，
实际结构由 CP0 冻结。保存失败、结果未知或文件损坏也不能顺带清空恢复区。

重启后的恢复、导出、丢弃由作者明确选择，不自动覆盖正式 Paper。恢复区本身写入失败要让作者知道。
强制终止测试只承诺找回最后一次成功持久化的草稿：刚输入但尚未写入恢复区的字，不能宣称必定恢复。

## 5. 同步和切换存储为何需要额外约束

本地文件列表能说明“当前看到了哪些路径”，无法独自说明云端文件是否已下载、远端是否有新版本，
或冲突版本是否全部保全。计划要求 Apple 原生发现、下载和文件协调；Core 负责 Paper 规则，
原生适配层负责取得和协调平台文件。

下面都是待验证的说明场景，不是当前应用已经通过的检查：

| 场景 | 需要理解的行为 |
| --- | --- |
| 作者从本地切到云端 | 先处理未保存内容与未决写入，再验证目标；失败时保留原选择，不自动搬文件 |
| 旧 Vault 的响应晚到 | 结果仍属于原存储和原草稿身份，不能更新新 Vault 的界面或清掉其草稿 |
| iCloud 关闭、账号变化或文件尚未下载 | 显示对应状态；不能悄悄改用本地 Vault，让作者以为仍在同步 |
| Mac 和 iPhone 离线修改后重连 | 保全并验证冲突版本，不按设备时钟挑赢家，不自动合并作者文字 |
| 两端离线创建了相同 code | 保留冲突并报告，不能通过改写历史 code 隐藏冲突 |

一次冲突处理可以按下面的顺序理解：

```text
发现冲突 → 保存并验证各冲突版本的原始字节 → 才能标记已处理
作者选择提升某个恢复版本 → 先保全当时活动版本 → 再安全替换
任一步失败或中断 → 保留已有副本与恢复状态，不能覆盖副本来重做
```

“已经保全冲突”表示版本有经验证的可恢复副本；它不表示系统替作者决定了最终文本。
损坏版本也需要按原始字节保全或导出，不能只留下解析成功的段落。相关约束见
[活动计划 §3](../../PLAN_road_v0_8.md#3-数据与交互合同)。

## 6. 怎样判断证据足够

阅读阶段报告时，先看它证明了哪一层，再看源码版本、平台、实际结果和遗漏。

| 证据 | 能支持的判断 | 仍不能代替的判断 |
| --- | --- | --- |
| 自动测试 | 被覆盖的解析、状态与失败分支符合预期 | 实体设备输入、真实云端往返 |
| 模拟器 | 对应模拟环境中的构建、调用和流程 | 实体 iPhone 的生命周期与输入表现 |
| 实体设备 | 记录中的原生操作、持久化和恢复确实发生 | 未检查的 provider 状态或其他分发构建 |
| 真实 provider | 实际共享容器、下载、冲突与两端往返结果 | 最终分发配置同样可用 |
| 作者验收 | 作者完成约定场景，开发者接受相应范围 | 未执行的场景或后续阶段自动通过 |
| 最终分发构建 | 指定渠道的实际候选满足已检查条件 | 其他渠道或其他候选同样可用 |

因此，CP5 接受开发候选后还不能直接开展首轮外部 Alpha。统一核心收口先完成，Road v0.9 再用
实际 TestFlight iOS 与最终 macOS 分发候选验证共享容器。切换分发渠道仍需检查相应候选。

文档检查只证明文档结构、预算与本地链接等检查项通过；它不启动 CP0，也不证明任何应用场景完成。
检查命令及更完整的证据解释见 [测试与证据手册](forfresh/testing-and-evidence-guide.html)。
